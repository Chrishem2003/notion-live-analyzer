# NEMA-AGORA Measurement Write Path — Security Design Gate

Status: **design only; no RPC is installed and no database writes are enabled**.

## Purpose

Define the minimum safe contract for adding durable indicator measurements to the proposed `nema_indicator_measurements` ledger. The current validator is in-memory only. Migration `004_nema_indicator_measurements.sql` is proposed and must remain unapplied until separately reviewed and approved.

## Trust boundaries

1. The Streamlit client is untrusted. It must never receive a Supabase service-role key or directly write to the ledger.
2. The NEMA API is the only planned write orchestrator. It must validate the service API key and a signed portal identity, then resolve the actor/role from trusted server-side identity data. Never accept a role selected by the browser as authoritative.
3. The database RPC is callable only by the server-side service role. Revoke execution from `PUBLIC`, `anon`, and `authenticated`. Do not grant direct table INSERT/UPDATE/DELETE to any API client role.
4. A database function receiving actor and role arguments cannot independently prove those values unless backed by a trusted identity mechanism. Therefore only the authenticated API may call it, and the API must derive those arguments from its verified identity object, not from the request body.

## Required RPC behavior before implementation

- Use a narrowly scoped `SECURITY DEFINER` function only if required; set a fixed safe `search_path` (for example, `pg_catalog, public`) and schema-qualify referenced objects.
- Accept one validated measurement payload plus an explicit idempotency key. Require the key to match the measurement ID or enforce a unique mapping between them.
- Validate actor ID, allowed role, indicator ID, definition version, reporting period, timezone, units, numeric fields, source/evidence reference shape, and status requirements again at the server boundary. Database constraints remain the final integrity gate.
- Permit new records only. No caller-facing update/delete operation. Corrections should be new versioned records or a separately reviewed supersession model; never silently overwrite evidence.
- In one transaction: insert the measurement, insert an append-only audit event, and record the idempotency key/result. Any failure must roll back all three writes.
- On retry with the same idempotency key and identical canonical payload, return the original result without duplicate records or audit events. If the same key is reused with a different payload, reject with a conflict.
- Use a database uniqueness constraint for idempotency; do not implement check-then-insert only in application code.
- Use optimistic concurrency only if the domain introduces mutable aggregate state. For an append-only measurement ledger, unique idempotency plus immutable records is preferred.
- Keep source/evidence references reviewable and stable. Do not put credentials, access tokens, unnecessary personal data, or raw sensitive documents in JSON fields.
- Never label a measurement `verified` merely because it was submitted. Verification must include an authorized reviewer, timestamp, evidence references, and a review event.

## Audit event minimum

Each accepted write should create an immutable event with: event ID, measurement ID, actor ID, actor role, action, timestamp generated by the database, idempotency key, and a canonical payload hash. Avoid storing full sensitive payload copies in the audit table. Deny UPDATE/DELETE on the audit table; table owner/function privileges must be reviewed because RLS alone does not constrain a table owner or `BYPASSRLS` role.

## Test gates

Before any staging apply or endpoint enablement, automated tests must cover:

- unauthenticated request and invalid signature are rejected;
- submitter cannot create or verify measurements;
- reviewer role cannot assign itself a higher role;
- direct client table writes are denied;
- same key + same payload is idempotent;
- same key + different payload returns conflict;
- measurement and audit writes are atomic under injected failure;
- audit events cannot be updated or deleted by application roles;
- invalid evidence, timezone, period, numeric values, and unsupported status are rejected;
- concurrent retries create exactly one measurement and one accepted-write audit event;
- secrets are never returned in API responses or logs.

## Rollout sequence

1. Keep this design and migration as review-only.
2. Implement and test the RPC in a disposable local database or isolated test project.
3. Review function ownership, grants, RLS behavior, search path, and audit immutability.
4. Obtain explicit approval for the exact staging project and migration.
5. Apply to staging only; verify grants and run tests with distinct client/server roles.
6. Deploy the API write endpoint disabled by default; enable only after staging evidence is recorded.
7. Production remains unchanged until a separate release approval.

## Current truth

- The Python validator validates payloads in memory.
- The proposed SQL ledger has no write grant.
- No transactional write RPC exists in this design note.
- No staging or production database was changed by creating this document.
